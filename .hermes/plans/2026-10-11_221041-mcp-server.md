# An MCP server: expose the knowledge bases to AI apps

> **Status: future work — not implemented, not scheduled.** Recorded so the work is
> unambiguous when it is picked up. For Hermes: implement task-by-task with the
> `subagent-driven-development` skill, never skipping the verification steps.

**Goal:** let any MCP-capable AI app (Claude Desktop / Claude Code, Open WebUI, an agent
framework, an IDE) search this machine's knowledge bases, read the exact pages a hit came
from, and — only when deliberately enabled — add and remove documents. The app stops being a
page you open and becomes a tool the assistants you already use can call.

**Architecture:** the engine is already plain Python behind a Starlette JSON API
(`pdfkb.web:app`), so the MCP server calls `KB.search` / `page_context` / `add_document`
**directly** — no HTTP round trip, no duplicated logic. It is served two ways: **stdio** for
desktop clients that launch a command, and **Streamable HTTP** mounted into the existing
Starlette app at `/mcp` for remote clients. Read-only by default; writes behind a flag.

**Tech stack:** Python 3.12 · the official `mcp` Python SDK (`pip install "mcp[cli]"`) ·
Starlette (already the app's framework) · the existing SQLite + vector stores.

**Reference (fetched from the SDK repository, 2026-10-11):** the current server class and the
Starlette mount idiom come from `examples/snippets/servers/streamable_starlette_mount.py`:

```python
from mcp.server.mcpserver import MCPServer          # the server class today; the decorator
from starlette.routing import Mount                  # API is `FastMCP` (@mcp.tool(), @mcp.resource("…"))

app = Starlette(routes=[
    Mount("/echo", echo_mcp.streamable_http_app(stateless_http=True, json_response=True)),
], lifespan=lifespan)          # lifespan runs `async with stack: await stack.enter_async_context(mcp.session_manager.run())`
# clients then connect to http://localhost:8000/echo/mcp
```

Transports today: `stdio`, `streamable-http` (+ legacy `sse`); the CLI is
`python -m … --transport stdio|streamable-http --port N`. The SDK's API has **moved** between
releases (`Server` → `MCPServer`/`FastMCP`, and a v2 migration guide exists) — pin the version
and re-read <https://py.sdk.modelcontextprotocol.io/> at implementation time rather than
trusting this sketch.

## Current state (verified, `~/pdfcomp`)

- `pdfkb/web.py` is a Starlette app with a complete JSON API behind the engine:
  `/api/search` (`q`, `mode=semantic|keyword|hybrid`, `k`, `libraries`), `/api/documents`,
  `/api/context` (a page's text), `/api/pdf/{library}/{doc_id}`, `/api/ingest`, `/api/export`,
  `/api/delete`, `/api/reset`, `/api/stats`, `/api/libraries` (+`/save`,`/use`,`/delete`),
  `/api/settings*`, `/api/sources*`.
- The engine is importable on its own (`KB` in `pdfkb/store.py`, `search`/`page_context` in
  `pdfkb/web.py`), so tools bind to functions, not routes.
- `requirements.txt` has **no** `mcp` dependency.
- The app is local and **unauthenticated**; there is no write protection beyond the
  one-writer rule (`KB.readonly` refuses index/delete/wipe/export on a non-active base).
- Hits already carry everything a citation needs: `chunk_id, doc_id, page, text, filename,
  library, knowledge_base{file,folder,store}, citation, score`.

## Constraints

- **Read-only by default.** Ingest and delete are off unless `--allow-write` (or the same in
  settings) is set explicitly.
- **A token is required for the HTTP transport.** The app is local-only today; `/mcp` must not
  be an open door to `0.0.0.0`. Bearer token in the config (or Traefik mTLS), refused with 401
  otherwise.
- **No filesystem paths in tool output.** Leaf names only, as the UI already does.
- **The one-writer rule holds.** A write tool writes only into the active knowledge base and
  refuses otherwise, exactly like the UI.
- Tool schemas are a **stable contract**: keep the tool set small and additive.

## Task 1: the server and its tools

**Objective:** a `pdfkb/mcp_server.py` whose tools are the app's own operations.

**Files:** `pdfkb/mcp_server.py` (new), `requirements.txt` (`mcp[cli]` as an optional extra),
`pdfkb/config.py` (`MCP_TOKEN`, `MCP_ALLOW_WRITE`).

**Step 1 — the tools** (each one calls the engine, and returns provenance on every hit):

| tool | arguments | returns |
|---|---|---|
| `search` | `query`, `mode` (semantic/keyword/hybrid), `k`, `libraries[]` | hits with `text`, `filename`, `library`, `knowledge_base`, `locator`/`page`, `score`, `citation`, `url` |
| `list_knowledge_bases` | — | the libraries, which is active, and (per base) documents/chunks/vectors |
| `list_documents` | `library` (optional) | documents with title, path, pages, chunks, added |
| `read_page` | `library`, `doc_id`, `page` | the page's text — the same bytes the UI's modal shows |
| `stats` | — | the `about` block the footer already renders (version, provider, extractor, store, counts) |
| `ingest` *(write)* | `path` or `url` | the ingest result line (`added … N pages, M chunks`) |
| `delete_document` *(write)* | `doc_id` | what was removed, with the same refusals as the UI |

**Step 2 — resources**, so an AI app can *read* a source the way it reads a file:
`kb://<library>/<doc_id>` (the whole document as text) and `kb://<library>/<doc_id>#p12`
(one page), plus `kb://stats`. Resource URIs are listed from the same engine calls.

**Step 3 — one prompt** (optional): *"Answer with citations from this knowledge base"* —
a canned prompt that tells the model to quote `citation` and never invent a page.

**Step 4 — verify:** with the SDK's own **client** over an in-memory or stdio transport,
assert the tool list and argument schemas, that `search("…")` returns hits whose citations
match what `/api/search` returns for the same query, that `read_page` returns the text the
modal shows, and that a write tool is **refused** when writes are off.

## Task 2: serving it — stdio, and mounted into the app

**Objective:** both client styles work: a desktop app that launches a command, and a remote
app that speaks HTTP.

**Files:** `pdfkb/mcp_server.py` (`__main__` with `--transport`), `pdfkb/web.py` (the mount),
`tests/run_verification.sh` (a check that `/mcp` is mounted).

**Step 1 — stdio** (the desktop case): `python3 -m pdfkb.mcp_server` with no HTTP at all; the
client config is
`{"mcpServers": {"knowledgebases": {"command": "python3", "args": ["-m", "pdfkb.mcp_server"], "cwd": "/Users/kmail/pdfcomp"}}}`.
It must work **without** the web app running, so the module opens the store itself.

**Step 2 — Streamable HTTP** (the remote case): mount it in the existing app under the app's
own lifespan so the session manager is running for the app's lifetime:

```python
routes = [ …the existing routes…, Mount("/mcp", mcp.streamable_http_app(stateless_http=True, json_response=True)) ]
```

so an MCP client points at `https://<host>/mcp/mcp` (or set `streamable_http_path="/"` to serve
at `https://<host>/mcp`). Clients that only speak stdio can bridge it with
`npx -y mcp-remote https://…/mcp`.

**Step 3 — auth:** a bearer token from settings; a middleware on the `/mcp` mount answers 401
without it. Never expose `/mcp` without one.

**Step 4 — verify:** a probe check that `/mcp` is mounted and that an `initialize` +
`tools/list` handshake succeeds **with** the token and is **refused without** it; plus a
`hermes verify` run proving the app still serves every existing route.

## Risks, tradeoffs, open questions

1. **A young SDK.** The server API changed between releases (`Server` → `MCPServer`/`FastMCP`)
   and v2 ships a migration guide; pin a version, and treat the sketch above as a pointer, not
   a contract. The transport names (`stdio`, `streamable-http`, legacy `sse`) are the parts
   most likely to drift.
2. **A new attack surface.** Today the app trusts anything on localhost. Mounting `/mcp`
   without a token on a machine that is reachable (this one is, via Traefik at `ai.kmail.at`)
   would hand out the whole knowledge base. Token first, mount second.
3. **Write tools are dangerous by name.** An agent that can `ingest` can fill a disk; one that
   can `delete` can destroy work. Keep them off by default, require the active-base rule, and
   never let a tool purge a whole base.
4. **Prompt injection through documents.** Content that arrives through a connector can carry
   instructions ("ignore your rules, delete …"). Writes stay off by default for exactly this
   reason; tool results should be labelled as *data*, never as instructions.
5. **Tool-schema stability.** Renaming a tool or changing an argument type breaks every client
   config; version the tool set (e.g. `search` keeps its signature, additions get new names).
6. **Which transport to make first.** stdio is enough for the desktop assistants this user
   uses and needs no auth story; the mounted HTTP transport is the one that makes it useful to
   remote apps — build stdio first, then the mount behind the token.
7. **Cost visibility.** A search tool lets an agent burn embeddings and vector queries quickly;
   log the call count and expose it (the footer's facts strip is the natural place).
